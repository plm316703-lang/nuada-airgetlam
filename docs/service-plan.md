## 2. 현업에서는 어떻게 하나

이 시스템은 성격상 두 가지 규제 영역에 걸친다. **임상 연구 소프트웨어**이면서, 뇌파로 로봇팔을 움직이면 **의료기기 소프트웨어**가 될 수 있다.
그래서 현업(병원 연구소, 임상시험 소프트웨어 회사, 의료기기 회사)은 "잘 돌아간다"만으로 배포하지 않고, **안전하다는 근거를 문서와 기록으로 남기면서** 배포한다.

### 2-1. 따르는 기준 (이름과 핵심만)

| 영역 | 기준 | 핵심 요구 | 이 프로젝트와의 관계 |
|---|---|---|---|
| 임상 연구 | ICH E6 GCP, 미국 21 CFR Part 11 (전자 기록·전자 서명) | **감사 추적**(누가·언제·무엇을·왜), 접근 통제, **시스템 검증**, 기록을 지우거나 고칠 수 없게 | 동의·철회·재개 기록, 감사 로그 |
| 의료기기 SW | IEC 62304 (SW 생명주기), **ISO 14971 (위험 관리)**, ISO 13485 (품질), IEC 62366 (사용 적합성) | 요구사항 → 위험 → 통제 → 테스트를 **추적표**로 연결, 모든 변경은 **변경 관리** | **관문 규칙 = 위험 통제 수단**. 이미 만든 것이 그대로 근거가 됨 |
| 사이버보안 | 의료기기 사이버보안 지침(FDA 등), SBOM | 사용한 라이브러리 목록(SBOM), 취약점 관리, 위협 분석 | 의존성 스캔, 이미지 스캔 |
| 개인정보 | 개인정보보호법(민감정보·가명정보), 생명윤리법(IRB), ISMS-P | 최소 수집, 가명 처리, 접근 기록, 기관 승인 | 익명 코드, 동의·철회 설계 (이미 있음) |
| 국내 의료기기 | 식약처 디지털의료제품 관련 법령·지침 | 소프트웨어 의료기기 허가·검증 | **범위 밖** (연구용 프로토타입으로 명시) |

> 이 표는 "이런 기준이 있고 우리가 어디에 해당하는지" 정리한 것이다. 인증을 받는다는 뜻이 아니다.

### 2-2. 현업의 개발·배포 흐름

```
 요구사항 ──▶ 위험 분석 ──▶ 설계(위험 통제) ──▶ 구현 ──▶ 검증(테스트) ──▶ 릴리스 ──▶ 운영
    │            │              │                            │              │          │
    └──────── 추적표(요구사항 ↔ 위험 ↔ 통제 ↔ 테스트) ─────────┘              │          │
                                                                          변경 관리   감사 추적
                                                                         (PR·승인)   모니터링·백업
```

| 현업 관행 | 하는 이유 |
|---|---|
| **환경 분리**: 개발 → 검증(스테이징) → 운영 | 운영 데이터를 개발·시험에 쓰지 않음. 검증 환경에서 합격한 것만 운영으로 |
| **변경 관리**: 모든 변경은 PR + 리뷰 + 영향 평가 + 승인 | "누가 왜 바꿨는지"를 나중에 설명할 수 있어야 함 |
| **시스템 검증(CSV)**: 설치 확인(IQ) · 기능 확인(OQ) · 실사용 확인(PQ) | 시스템이 의도대로 동작한다는 **증거**를 남김 |
| **추적표** | 요구사항 하나하나가 어느 테스트로 확인됐는지 보여 줌 |
| **릴리스 버전 + 릴리스 노트** | 어떤 버전이 언제 운영에 나갔는지, 무엇이 바뀌었는지 |
| **공급망 보안**: 의존성·이미지 취약점 검사, SBOM | 남이 만든 라이브러리의 구멍도 내 책임 |
| **코드로 서버 구성(IaC)** | 서버가 날아가도 같은 환경을 30분 안에 다시 만듦 |
| **SOP(표준 작업 절차)** | 배포·장애 대응·백업 복원을 사람마다 다르게 하지 않음 |
| **파일럿은 기관 내부망에서** | 병원·연구기관은 보통 외부 클라우드보다 **기관 내부 서버(온프레미스)**나 기관이 승인한 클라우드에 먼저 설치 |

### 2-3. 우리는 무료로 이렇게 흉내 낸다

| 현업 | 우리 프로젝트 (전부 0원) |
|---|---|
| 개발 / 검증 / 운영 환경 | **로컬(개발)** / **무료 서버(스테이징 = 파일럿)** — GitHub Environments로 구분 |
| 위험 관리 파일 (ISO 14971) | `docs/quality/risk-register.md` — 위험원(잘못된 명령이 팔을 움직임 등) → 원인 → **관문 규칙(통제)** → 검증 테스트 |
| 추적표 | `docs/quality/traceability.md` — 요구사항 ↔ 위험 ↔ 코드 ↔ 테스트 이름 (테스트 29개가 이미 근거) |
| 변경 관리 | **브랜치 보호**(main 직접 push 금지, CI 통과·리뷰 필수) + **PR 템플릿**(변경 이유, 영향받는 위험 번호, 테스트 증거) |
| 시스템 검증 IQ/OQ | CI 테스트 리포트 보관(OQ) + 배포 직후 자동 점검 스크립트(IQ) → `docs/quality/validation/` 기록 |
| 릴리스 | Git 태그 `v0.1.0` + GitHub Release 노트 + `CHANGELOG.md` |
| 감사 추적 | `audit_logs` (추가만 가능, 수정·삭제 불가) + **재개·초기화 때 사유 입력 필수** |
| 공급망 보안 | Dependabot(의존성), CodeQL(코드 분석), Trivy(이미지 취약점), SBOM 생성 — 공개 저장소 무료 |
| IaC | 서버 설치 스크립트(cloud-init) 하나로 빈 서버 → 서비스 기동 |
| 비밀 관리 | GitHub Secrets + 서버 `.env`(권한 600) |
| 모니터링 | UptimeRobot 무료(5분 간격) + 메일 알림 |
| SOP | `docs/sop/` — 배포, 백업·복원, 장애 대응, 계정 발급·회수, 권한 정기 검토 |

## 3. 무료로 서버를 어디에 두나

| 선택지 | 비용 | 장점 | 주의 |
|---|---|---|---|
| **A. Oracle Cloud Always Free (ARM)** | 0원 | 외부에서 항상 접속, 2코어/12GB로 전체 스택 여유, 실제 클라우드 운영 경험 | 가입 때 **카드 등록**(본인 확인, 무료 범위면 청구 없음). **7일간 CPU·네트워크·메모리 사용률이 모두 20% 미만이면 회수될 수 있음**. 인기 리전은 용량 부족으로 생성이 안 될 때가 있음. 2026-06에 무료 한도가 4코어/24GB → 2코어/12GB로 줄었다는 보고 (확인 필요) |
| **B. 연구실(내) PC 온프레미스** | 0원 | 현업 파일럿과 가장 비슷(기관 내부 서버), 카드 불필요, 지금 Docker 구성 그대로 | PC를 켜 둘 때만 접속. 외부 접속은 **Cloudflare Quick Tunnel**(계정 불필요, 매번 주소가 바뀜, 가동 보장 없음)로 시연할 때만 |
| ~~AWS~~ | 월 약 $25 | | 무료 플랜은 6개월·크레딧 소진 시 정지 → **폐기** |

**AI 제안: A를 스테이징(파일럿) 서버로, B를 예비로.**
A의 회수 위험은 현업의 IaC 방식으로 대비한다. 서버는 언제든 사라질 수 있다고 보고, **설치 스크립트 + 백업**으로 30분 안에 다시 만든다.

A를 쓰면 ARM 서버이므로 Docker 이미지를 **amd64 + arm64 두 종류로 빌드**해야 한다 (GitHub Actions에서 무료).

## 5. 단계별 계획

각 단계 = 새 브랜치 → 구현 → 테스트 → PR → 머지 (지금 Git 흐름 그대로). 현업 순서대로 **"일하는 체계"를 먼저** 만들고, 그 체계 위에서 기능을 바꾼다.

### 1단계 — 저장소 운영 체계 (1~2일) ← 현업의 기본기

| 할 일 | 현업 의미 |
|---|---|
| GitHub Actions CI: MySQL 컨테이너로 `gradlew test`, Python 문법 검사 | 검증(OQ) 자동화 |
| 브랜치 보호: main 직접 push 금지, CI 통과 필수 | 변경 관리 |
| PR 템플릿: 변경 이유 / 영향받는 위험 번호 / 테스트 증거 / 화면 캡처 | 영향 평가 |
| Dependabot, CodeQL, Trivy, SBOM | 공급망 보안 |
| `CHANGELOG.md`, 첫 태그 `v0.1.0` (지금 상태) | 릴리스 관리 |

**완료 기준**: 일부러 테스트를 깨뜨린 PR이 머지 버튼 비활성화로 막힘.

### 2단계 — 품질 문서 (2일) ← 포트폴리오 차별점

| 문서 | 내용 |
|---|---|
| `docs/quality/requirements.md` | 요구사항 번호 붙이기 (예: REQ-GATE-04 "2초보다 오래된 명령은 실행하지 않는다") |
| `docs/quality/risk-register.md` | 위험원 → 원인 → 심각도·가능성 → **통제(관문 규칙·워치독·수동 재개)** → 남은 위험 |
| `docs/quality/traceability.md` | REQ ↔ 위험 ↔ 코드 ↔ 테스트 (`ArmSupervisorTest.watchdog` 등) |
| 빠진 테스트 보충 | 추적표를 만들다 보면 테스트가 없는 요구사항이 드러남 → 채움 |

**완료 기준**: 모든 위험 통제 수단에 연결된 테스트가 1개 이상.

### 3단계 — 운영 안정성 (3~4일)

| 할 일 | 내용 |
|---|---|
| 설정 분리 | `application-prod.yaml`: 시연 계정 끔, `ddl-auto: validate`, SQL 로그 끔 |
| **Flyway** | 테이블 8개 → `V1__init.sql`, 이후 변경은 `V2__…`로만 |
| 헬스체크 | Spring Actuator `/actuator/health` |
| 백업·복원 | 매일 `mysqldump` 7일 보관 + **복원 절차 SOP**와 복원 연습 기록 |
| 로그 | Docker 로그 회전(10MB × 5) |
| 재생기 분리 | `docker-compose.prod.yml`에서 재생기 제외 (연구실 PC에서 실행) |

**완료 기준**: 빈 DB → Flyway → 테스트 통과, 백업 파일로 다른 DB 복원 성공.

### 4단계 — 계정·보안·감사 추적 (4~5일)

| 할 일 | 내용 |
|---|---|
| 계정 발급·비활성화 | 관리자 화면, 공개 가입 없음, 첫 로그인 비밀번호 변경 강제 |
| 로그인 잠금 | 연속 N회 실패 → M분 잠금 (D2) |
| **감사 추적** `audit_logs` | 누가·언제·무엇을·**왜**. 추가만 가능 (DB 권한으로 UPDATE·DELETE 막음) |
| 재개·초기화 **사유 입력** | 현업 전자 기록 기준: 중요한 조작에는 사유를 남김 |
| **장비별 API 키** `devices` | 키는 해시로만 저장, 폐기 가능 |
| 보안 헤더 | CSP, HSTS, X-Frame-Options |

**완료 기준**: 잠금·감사 추적·키 폐기 테스트 추가, 추적표 갱신.

### 5단계 — 스테이징(파일럿) 서버 배포 (2~3일)

| 할 일 | 내용 |
|---|---|
| 서버 생성 | Oracle Always Free ARM, Ubuntu 24.04 (선택지 B면 연구실 PC) |
| 설치 스크립트(IaC) | Docker 설치 → 방화벽 → 저장소 내려받기 → `.env` 안내 → 기동. **빈 서버에서 한 번에** |
| 방화벽 | 22는 내 IP만, 80·443만 공개 (3306·8080·8000 비공개) |
| DuckDNS + nginx + Let's Encrypt | HTTPS, WebSocket 프록시, 인증서 자동 갱신 |
| 다중 아키텍처 이미지 | Actions에서 amd64 + arm64 빌드 → ghcr.io |
| 배포 | **릴리스 태그 + 승인 버튼(GitHub Environments)** → SSH 배포 → 자동 점검(IQ) → 실패 시 이전 버전 |

**완료 기준**: 휴대폰 LTE에서 HTTPS 로그인, 연구실 PC 재생기가 `wss://`로 연결, **서버를 지우고 스크립트로 다시 만들기 30분 이내**.

### 6단계 — 파일럿 운영 (2일)

| 할 일 | 내용 |

**완료 기준**: PQ 기록 1건, `v1.0.0` 파일럿 릴리스.
